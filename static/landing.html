This is a working RAG chat app wrapped end-to-end by rag-guard (internally "JEV"): a typed-decision layer that checks whether retrieval actually found something relevant, whether there's enough of it to answer confidently, and whether the model's answer is actually supported by what was retrieved -- before you ever see a confident-sounding guess.

The problem this guards against

Vector search finds passages that are embedding-close to a query -- that's not the same thing as "this passage answers the query" or "the model's answer is actually backed by it." Most RAG hallucination isn't the model lying; it's being handed a context that doesn't contain the answer, and doing its best anyway.

Silent gap

Retrieval misses the one chunk that actually answers the question, and nothing downstream knows to say so.

Confident guess

The context is too thin to answer, but the model answers anyway -- fluently, and wrong.

Unverifiable claim

The final answer reads fine on its own; you have no way to tell which parts of it the source text actually supports.

How rag-guard decides

Every query in this app runs through the same seven-stage pipeline. Each stage is a single bounded, calibrated judgment -- not a free-form model call -- so it's cheap, fast, and auditable: a probability you can threshold and log, not prose you have to parse. The app's own "Why this answer?" trace shows you exactly which stage decided what, for every reply.

1
Intent
Should this query even reach retrieval, or does it need to be escalated to a human or refused outright?
proceed / escalate / refuse
2
Relevance
Does this retrieved passage actually help answer the query? Drops noise before it reaches anything else.
kept / dropped per chunk
3
Clarify
Is the query itself too ambiguous to answer from what was kept, regardless of how good the context is?
clarify
4
Sufficiency
Is the kept context enough to answer confidently -- fully, partially, or not at all? A "no" here skips generation entirely.
insufficient_context
5
Generate
Only now does the LLM actually run, against exactly the chunks that survived relevance filtering.
1 LLM call
6
Grounding
Split the answer into claims and check each one against the retrieved context. Flags drift instead of hiding it.
ungrounded_answer_flagged
7
Caveat
Even a fully grounded answer can need a caveat -- partial coverage, an edge case the source text itself hedges on.
answered_with_caveat

Two ways to see it work

Upload any .txt, .md, or .pdf -- there's no pre-built demo corpus here on purpose. The point is proving this works on a document neither rag-guard nor the model has ever seen.

Single provider

Chat normally, with every reply backed by a visible reasoning trace.

  • Which chunks were kept vs. dropped, and at what probability
  • The sufficiency gate's probability against its threshold
  • A per-claim grounding breakdown -- supported / unsupported

Compare mode

Run the same question through two embedding providers at once, to see retrieval quality differences directly instead of taking them on faith.

  • OpenAI text-embedding-3-small vs. Google gemini-embedding-001
  • Raw answer (guard off) next to the JEV-protected answer, per provider
  • Same chunks, same thresholds, same generation model -- only retrieval differs

rag-guard is a real external dependency here, not embedded logic

This app installs rag-guard the way any other project would -- over pip, pinned to a commit -- specifically to prove the published package behaves the way its own docs and test suite claim once something outside its own repo actually depends on it.

from rag_guard import RagGuard guard = RagGuard(model=decision_model) report = guard.run(query, chunks, generate_fn) assert report.action in ("answered", "answered_with_caveat", "insufficient_context", "ungrounded_answer_flagged", "clarify", "escalate", "refuse")
The judgment calls themselves come from a pluggable decision model -- this app can run on any of them without changing a line of pipeline code:
